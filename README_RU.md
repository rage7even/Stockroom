# Stockroom — учебная версия

Angular + Django + SQLite. Рабочая система одного склада аксессуаров телефонов. Сохранены оформление и основные страницы первоначального frontend; backend переписан с использованием стандартных пользователей, паролей и сессий Django.

## Быстрый запуск на Windows

1. Распакуйте весь архив, например в `C:\Projects\Stockroom_Study`.
2. Проверьте `py -3 --version` или `python --version`. Подойдёт установленный Python 3.11 или новее, в том числе из MSYS2. Если `py` не находит подходящую версию, `setup.bat` использует `python` из PATH.
3. Запустите `setup.bat`. Интернет нужен для первой установки двух Python-зависимостей. Этот шаг создаёт таблицы и вымышленные данные, если база пуста.
4. Запустите `start.bat` и оставьте окно открытым.
5. Откройте **http://127.0.0.1:8000**.
6. Остановка — Ctrl+C. Данные сохраняются после перезапуска.

Если вы распаковали учебный архив с готовой сборкой Angular, Node.js для запуска не нужен. Если вы клонировали репозиторий GitHub, сначала соберите frontend по [английской инструкции](README.md#run-it-on-windows). Открывайте приложение через сервер Django. Это локальная версия на одном ноутбуке; для доступа с других устройств понадобится отдельная настройка.

| Роль | Логин | Пароль |
|---|---|---|
| Manager | manager@stockroom.local | Stockroom2026! |
| Sales | sales@stockroom.local | Stockroom2026! |
| Admin | admin@stockroom.local | Stockroom2026! |

Кнопки demo заполняют поля; затем нажмите Sign in. Все данные и аккаунты демонстрационные. Начальный набор: 18 товаров, 3 клиента, 3 заказа. Регистрация сохраняет нового пользователя и выдаёт роль sales. Только admin управляет сотрудниками по **http://127.0.0.1:8000/admin/**. Для новой роли sales/manager не выдавайте флаги staff/superuser; эти флаги нужны только администратору Django.

Если двойной клик не работает, откройте терминал в корне и выполните:

```powershell
# Если папки .venv ещё нет, создайте её через python -m venv .venv
# или py -3 -m venv .venv, в зависимости от того, какая команда доступна.
$stockroomPython = '.\.venv\Scripts\python.exe'
if (-not (Test-Path $stockroomPython)) { $stockroomPython = '.\.venv\bin\python.exe' }
& $stockroomPython -m pip install -r backend\requirements.txt
& $stockroomPython backend\manage.py migrate
& $stockroomPython backend\manage.py seed
& $stockroomPython backend\manage.py run_stockroom 127.0.0.1:8000 --noreload
```

Задайте `$stockroomPython` по тому же примеру в каждом новом окне PowerShell, где используете команды ниже.

## Что демонстрировать

- Регистрация, вход и выход с настоящими Django-сессиями.
- Overview: показатели, дефицит, последние заказы, старые резервы.
- Products: поиск, фильтры, карточка, добавление и редактирование manager/admin.
- Orders: несколько товаров, два sales channel, подтверждение, упаковка, отгрузка и отмена.
- Receiving: приёмка и коррекция, SKU сканером HID или вручную, запись автора и причины.
- History: кто, когда и почему изменил физический запас или резерв; фильтр и поиск.
- Customers: одна запись на магазин, связь с его заказами.
- Автоматическая локальная backup-копия и CSV старых резервов.

Чтобы увидеть изменения другого пользователя, нажмите **Refresh data** в верхней панели. После собственных изменений данные обновляются автоматически. Постоянного фонового опроса и WebSocket нет — это облегчает объяснение frontend.

Основное правило: **available = on shelf − reserved**. Активные резервы принадлежат confirmed и packed заказам. При подтверждении физический запас не меняется. При отмене освобождается резерв. При отгрузке уменьшается физический запас и одновременно закрывается резерв.

## Понятная структура

| Папка / файл | Для чего нужен |
|---|---|
| frontend/src/app/*.ts и *.html | Отдельные компоненты страниц и их шаблоны |
| frontend/src/app/store.ts | Запросы к API и данные, которые отображают страницы |
| frontend/src/styles.css | Общее оформление; не нужно заучивать каждое CSS-правило |
| backend/inventory/models.py | Таблицы и связи |
| backend/inventory/serializers.py | Проверка данных, поступивших из форм |
| backend/inventory/views.py | Получить запрос, проверить роль, вызвать функцию и вернуть JSON |
| backend/inventory/services.py | Проверка запаса, заказ, отмена, отгрузка, приёмка |
| backend/config/urls.py | Адрес API → обработчик |
| backend/inventory/tests.py | Проверки бизнес-логики и авторизации |
| database/queries.sql | Три SQL-запроса для демонстрации |
| docs/TEAM.md | Имена, файлы и порядок индивидуальной защиты |
| docs/CRITERIA.md | Связь с заданиями и честный статус требований |

Пример пути данных: Products → Store.request('/products') → urls.py → views.products → services.inventory → Django ORM → SQLite → JSON → Angular table.

Вход, хеширование пароля, cookie сессии, CSRF-защиту и административную страницу предоставляет Django. Не требуется объяснять собственный криптографический алгоритм. CSRF-токен передаётся в заголовке X-CSRFToken: это стандартная защита Django для изменений через браузер.

## Работа с frontend

Для изменения Angular установите Node.js 22.22.3+ из ветки 22 либо совместимую версию из официальной таблицы Angular. Откройте два терминала:

```powershell
# Терминал 1, корень проекта
& $stockroomPython backend\manage.py runserver 127.0.0.1:8000
```

```powershell
# Терминал 2, корень проекта
cd frontend
npm.cmd ci
npm.cmd start
```

Откройте http://127.0.0.1:4200. Proxy отправляет /api на 8000. Пользуйтесь одинаковым hostname: везде 127.0.0.1, чтобы cookie работали ожидаемо.
После изменений выполните `npm.cmd run build` в frontend, чтобы start.bat показывал новую сборку. Для разработки через обычный runserver фоновые backup-проверки не запускаются; команда run_stockroom в start.bat включает их.

## Проверки

```powershell
& $stockroomPython backend\manage.py test inventory --noinput
& $stockroomPython qa\http_check.py
```

Первый запуск: 15 тестов, включая 20 записей в test_15. Тестовая БД отдельная, рабочие данные не меняются. Второй запуск: реальный временный HTTP-сервер, 20 клиентов и конкурентные заказы на копии демонстрационной БД. Для повторяемых исходных чисел HTTP-проверка использует database/demo.db.

Результаты исходных проверок на Linux находятся в qa/tests.txt, qa/data_results.csv, qa/http_results.json и qa/backup_result.json. На Windows с Python 3.11 из MSYS2 дополнительно проверены setup.bat, запуск через start.bat, вход менеджера по HTTP и выдача 18 товаров из демобазы. Все 15 тестов Django прошли. Для полного сценария в браузере используйте qa/manual_checks.csv.

## Копии и сохранность

При запуске start.bat и затем каждый час проверяется возраст последней копии. Если прошло более суток, создаётся проверенный SQLite snapshot; сохраняются последние 30 копий. Отчёт stale_reservations.csv перечисляет незакрытые резервы старше 14 дней. Менеджер решает, отменять или отгружать: автоматической отмены нет. Писем система не отправляет.

Ручной запуск:

```powershell
& $stockroomPython backend\manage.py maintenance
```

Копии находятся в backend/backups. Переносите их на защищённый внешний носитель. Копии на том же ноутбуке не защищают от потери всего устройства. Сервер, который выключен, фоновые задачи не выполняет. История склада автоматически не очищается, UPDATE/DELETE запрещены триггерами. Реальный год хранения пока не прошёл.

Для восстановления остановите сервер и программы, открывшие БД, затем:

```powershell
& $stockroomPython integration\restore.py backend\backups\ИМЯ_КОПИИ.db --server-stopped
```

Укажите настоящее имя файла. Скрипт сохраняет предыдущую БД и очищает сессии после восстановления. Не используйте старые базы из других версий: эта версия имеет новую обычную Django-схему. Старые архивы остаются отдельными; перенос данных между версиями в объём этого учебного варианта не входит.

Чтобы повторить показ с исходными остатками: остановите сервер, переименуйте backend/stockroom.db, затем выполните migrate и seed. Исходная учебная копия также включена в database/demo.db.

## Границы и вклад

Система сохраняет основной процесс и обещания 10-й недели. Большой модуль закупок, Docker, QR/экспорт и отдельная панель управления backup не включены. Их ранее предлагали как будущие задачи, а не как подтверждённые обязательства команды.

Hardware-план, USB-политика и закупка оборудования — организационная часть проекта. Программный ввод SKU вручную есть; физические сканер, принтер, USB-lock и внешний SSD не тестировались. Отдельный публичный магазин и оплата не входят в эту версию; website — значение канала заказа.

Код собран ИИ на основе двух вариантов команды и прошлых требований. Каждый должен изучить свой модуль, повторить проверки и записать реальное личное изменение в docs/CONTRIBUTION.md. Порядок работы в командном репозитории описан в [TEAM.md](docs/TEAM.md).
